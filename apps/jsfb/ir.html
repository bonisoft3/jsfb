jsfb — the row operations, one at a time

This app is a reference. Every operation in it exists because it forces a different part of this terminal's write contract into the open, and the benchmark is what says whether the result is right.

Overview

js-framework-benchmark's page, compiled from brief.md (pinned above) onto the mecha cluster, the omnishell terminal, the sayt loop and the bayt build graph. Two entities, one screen, nine operations. Both entities take the tab path: nothing is published, no migration is emitted, and the whole data plane is the terminal's in-memory collections. No pipeline, no handler beyond the one fold, no escape hatch (decision-08), because a benchmark that reached outside the terminal would be measuring something else.

The load-bearing idea is that every operation is one fold over the rows, and none of them is a form. The benchmark's six buttons and the two links in each row are the published markup's, and each click reaches the bench reduce carrying the row's id and the element's own DOM id and nothing else (decision-03). The reduce answers with puts, patches and deletes, and the two regions — one over Bench, one over Row — redraw what changed. The other two ideas are that position and selection are both columns (decision-04, decision-06), so a swap is two writes and a selection at most two, whatever the table's length.

Because the operations are a function of the rows, they are checkable without a browser or a cluster: the loop's ops check drives the fold directly (invariants). The timings under what the benchmark measures need a driver outside the page, and are the one thing here the ladder does not grade.

Entities

Row — tab

The table under test. A row is an id, a label of three words, its position, and the class it wears when selected. The id is the bench counter's value when the row was made, so ids climb for the life of the page and are never reused; the same counter is the row's place in the label walk (decision-02) and its ord, so a new row always sorts after every row that exists. ord is what the region orders by, which is what lets Swap Rows be two rows exchanging it (decision-04). cls is the literal class the benchmark's selected row wears, because a template binds a field and cannot compose one (decision-06). Nothing is seeded: the page starts with no rows, as the benchmark's does.

labelstringthis.size() >= 3 && this.size() <= 60one adjective, one colour, one noun; Update every 10th appends " !!!"
ordint32this >= 0the position the table draws the row at; a swap exchanges two of these
clsstringthis in ['', 'danger']optional; danger on the selected row, the empty string on every other

Bench — tab

One row, seeded as bench, that the fold reads and settles on every operation that needs to remember something across clicks. next_id is the next id to hand out, so Create and Append never repeat one and a refill never has to keep clear of its own deletion (decision-05). picked is which row wears the selection, so clearing the last one is a lookup and not a walk of the table (decision-06). The screen's outer region is over this row, and the whole page is its item template — the jumbotron, the six buttons and the table are drawn once the seeded row arrives.

Screens

main — the benchmark's page

Reads: Bench (filter id=eq.bench, order id.asc) as the outer region, whose one item is the page; Row (order ord.asc) as the table nested inside it, one <tr> per row with the id in the first cell, the label as the lbl link in the second and the ✕ as the remove link in the third. The table's empty text is the empty string: a table with no rows shows nothing under the buttons, as the benchmark's does. Both regions name bench as their handler and declare no mutation handler, because the fold answers clicks and nothing else (decision-05).

Mutations: no form — the program's forms is empty, so there is no form contract here. The control region is the benchmark's six buttons — run, runlots, add, update, clear, swaprows — each carrying its published id and a click binding to bench; the label link carries the row and the ✕ link carries the row in its own id, rm-{id}. Every one of the nine operations is one fold (flows). Element ids, class names, the four-cell row and the captions are the published implementation's (decision-01); the palette is the press preset's roles (DESIGN.md), and both of the preset's list keyframes are rebound to no animation (decision-07).

Flows

Every flow is the same shape: a click on one of the benchmark's own elements reaches the bench fold with the row's id and the element's DOM id, the fold returns an array of puts, patches and deletes, the store applies them, and the two regions redraw what changed. What differs is what the fold states, and against which table.

Invariants

The program declares no test objects, and this document carries no test pairs, because the operations are a function of the rows and the loop grades the fold directly: the ops check under the test verb runs tests/ops.ts, which loads bench.js, clicks each control by its DOM id against a given table, applies the returned writes and asserts what follows. No browser, no cluster, milliseconds. What it holds the fold to is below; each line is one of the acceptance list's promises restated over the fold's output, with input the rows and bench row given and output the writes returned.

Counts. Append from nothing gives output.rows.size() == 1000; Create-1,000 over a thousand rows states output.deletes.size() == 1000 and leaves a thousand, none of them a row that was there (output.rows.all(r, int(r.id) > input.bench.next_id - 1)); Create-10,000 leaves ten thousand; Create over an empty table states no absence at all; Clear states every row absent and output.bench.picked == ''.

Ids and order. Ids climb from the bench counter and the counter advances past what it handed out: output.bench.next_id == input.bench.next_id + 1000. ord is dense and starts where the ids start, and an appended row sorts above every row that existed — which is what lets a later Create's absences and arrivals be one array.

Labels. Every label is three words, and consecutive labels differ in all three (decision-02).

Update. Exactly a hundred of a thousand rows gain the suffix, and they are the rows at positions 0, 10, 20 … by ord: output.patched.all(p, p.pos % 10 == 0) && output.patched.size() == 100.

Swap. Positions 1 and 998 exchange and every other position holds; the swap is exactly two row writes (output.rowWrites.size() == 2); a table of 998 rows or fewer writes nothing.

Select. With nothing picked, selecting is the row and the note (output.size() == 2) and the row gains danger; selecting another is three writes, one row gaining the class and one losing it, whatever the table's length; selecting the row already picked writes nothing.

Remove. The row's ✕ drops exactly the row its DOM id names (output.size() == 1 && output[0].op == 'delete'), leaves the rest standing, and selects nothing.

Decisions

The benchmark is the oracle, and it is reproduced rather than interpreted. Element ids (run, runlots, add, update, clear, swaprows), class names (test-data, lbl, remove, danger), the four-cell row and the button captions are the published implementation's. A nicer arrangement of them would cost the app the only thing it is for: being recognisable to anyone who has read any other implementation of the same benchmark.

Labels are a walk through the lattice, not a sample from it. The reference implementation draws each of the three words with Math.random, which a compartment does not have. Each index here advances by its own stride — one, seven and five, each coprime to the list it walks — so consecutive labels differ in all three words and the walk is 3,575 long before it returns to its start. It yields 3,250 distinct labels rather than 3,575, because the colour list holds "brown" twice; that repetition is the benchmark's and is kept. The output has the shape of a sample and the app replays, which is worth more here than sampling was.

A click carries ids, so the buttons wear them. A handler event is the row's id and the element's own DOM id, with no payload. Selecting a row needs only the first. The two buttons that also speak to the reduce carry id="run" and id="runlots" and are told apart by the second — which is what those attributes are for in the benchmark anyway.

Position is a column, and a swap exchanges it. A region draws its rows in the order a column names, so the table carries ord and Swap Rows gives two rows each other's value. The observable move is the array swap every other implementation performs — the rows at positions 1 and 998 change places and their ids travel with them — and it costs two writes rather than a thousand.

Removing is the fold's, not a form's. A reduce states three things about a row — that it is this, that these fields of it become that, or that its key has no row — so every one of this benchmark's nine operations is one fold, and none of them needs a form. Clear states the absence of every row it can see. The row's ✕ states the absence of one, and carries which in its own DOM id, because the label beside it carries the same row and a click says nothing else about which was hit. Create-1,000 and Create-10,000 state both halves at once, the absences and the thousand arrivals in one array, so no counter has to keep a refill clear of its own deletion. The control region is what the benchmark's is, six buttons and no form, and the table's only other element is the label.

What that is worth here is not tidiness. A form per row is the most expensive element a long list can carry in Chromium (see below), so the row's ✕ ceasing to be a form is what takes Create-10,000 from 1097ms to 369ms and clearing ten thousand from 646ms to 257ms.

Which row is selected is a column too. Clearing the last selection means finding the row that wears the class, and reading it off the table is a walk of every row to answer a click on one. The bench row carries the id instead, so selecting is two row writes and a note of which, whatever the table's length.

The selected row's class is a column. A template binds a field and cannot compose one, so cls holds the literal word danger and the row binds class="{cls}". Selecting writes at most two rows — the one that gains the class and the one that loses it — because restating the other nine hundred and ninety-eight would be a thousand mutations saying nothing.

A row arrives and leaves at once. The preset gives every list an enter and an exit keyframe, and a row on its way out stays in the list until its exit has played. The benchmark's rows play nothing, and its oracle times a removal to the row being gone, so the screen rebinds both slots to no animation — the binding the preset declares rebindable for exactly this. Removing a row is then the fold, the store and one frame, which is what the reference measures too.

Escape hatches: none. No container, no WASM unit, no vendored component, no external endpoint: hatches and vendored are empty and blobs is false, so the program's cluster unification and the emitted bayt.cue redeclaration carry no changes. The one piece of app code is the bench fold, a compartment the terminal already runs for any handler. The point of this app is to measure the terminal's write contract, and a benchmark that reached outside the terminal would be measuring something else.

What the benchmark measures

Against the React reference in bench/react — the canonical keyed implementation, rows in an array and React reconciling — in the same browser through the same driver (bench/h2h.ts), timed from the click to the last change under the table, median of seven fresh-page runs.

Replacing a thousand rows is even: a thousand leave one at a time around a thousand arriving, and the reference reconciles the same. The two clears are lost to the data plane, and both losses are the same shape. The collection under a tab table keeps its keys in a sorted array and splices per row, so a fold stating ten thousand absences in key order moves half the array per row — forty milliseconds, and quadratic in the table. And a local tier's write still builds a transaction, a mutation object and a UUID per row, for a collection with nothing to be optimistic against — thirty-three more. Both live in the vendored engine, below anything this terminal decides, and are recorded on the client's upgrade note. Taking a thousand rendered rows out of Chromium's layout tree is the other three and a half milliseconds, and React pays that too.

What the numbers rest on

A whole-table read gets no view. The collection is that set already, and the snapshot is sorted at read. A maintained view over it keeps the order by moving array elements — its sorted map and its top-k operator both splice per row — so a bulk write is quadratic in the table: 197 ms of clearing ten thousand rows, on top of the collection's own. The region still hears which rows moved: the snapshot subscription carries the delta.

A node is wired once, when it arrives. Its listeners outlive every later refresh, so a write to a list of ten thousand rows wires the arrivals and walks nothing else. Wiring every standing row on every write is what made appending a thousand rows cost the two thousand on screen. plugins/omnishell/test/bind-scale.test.ts holds the count.

A wake is a posted message, not a zero-delay timer. The browser clamps a repeated timer to four milliseconds, and a region wakes once per write, so every write past the first few paid the clamp.

Two things the measurement itself taught. A subscription in the engine is told only of keys it has seen, so one opened after a seeded row exists never hears that row's delete; the store opens every subscription with initial state declared off, which the engine takes as every key already seen. And on this machine an idle renderer thread lands on an efficiency core, where the same work takes three times as long, so the driver warms the thread before each click, for both sides.

Only a change of growth rate earns a mechanism. Every operation here can be made faster than React — compiling the item template into a binding plan, feeding a tab collection through the sync side, and flushing a wake at the end of the write that raised it do it, create-10,000 by six times. Each is a constant factor bought with a mechanism of its own, and the first two carry an invariant a test DOM breaks. The terminal keeps what alters how cost grows with the table and leaves the constants to the engine upgrade; the two clears above are the price, and it is stated.

What a form per row costs, and why there is none here. Touching a <form> from JavaScript — any element API on it: getAttribute, matches, classList, dataset, closest, addEventListener — makes every subsequent DOM insertion anywhere in that document cost time proportional to the number of forms so touched. Ten thousand touched forms cost 48us an insertion; ten thousand untouched ones, or ten thousand touched <div>, <fieldset> or <section> elements, cost nothing. It scales with the count: 3us at a thousand, 21us at five thousand, 49us at ten. Firefox and WebKit charge nothing at all, so it is Chromium's and not the platform's; repro/form-insertion-cost.html is the finding without the terminal in it. A terminal cannot avoid the touch: binding a region asks every element what it declares. That is what the reduce learning to delete (decision-05) bought: with the row's ✕ no longer a form, the list stopped being quadratic in its own length.

The benchmark's own timings are not collected by the page. Timing an operation needs a driver outside it, because a reduce has no clock to read one with.
